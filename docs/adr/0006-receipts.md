# ADR-0006：動作結果與付款結果

狀態：已採用（2026-09-28）。規則版本：CR 1.27.0。

## 背景

BP03-001 的起動費用取童話 counter，Q443 對 X 的使用要求保留實際取走量。BP13-SL16 的 Q1776 則需要分辨同一批中 token 建立成功、原卡移動失敗。只有一個 did 布林無法表示兩者；把移動量當付款是否完成也會出錯。

CR 10.6.2.5.2–.3 容許規則取代或零費用仍算支付，.5.4 要在付不起時回復到選擇打出之前。BP03-088 的隨機捨牌成本進一步要求回復涵蓋 RNG 與已對外資訊，不能先揭示隨機結果再決定取消。

## 決定

每個 I 指示產生 typed receipt，記 requested／actual 單位、status、成功成員、before／after、moves、replacements、payment 與 reason。PaymentComplete 與物理動作事件分開；合法零費用不製造移動事件，合法取代可完成付款但只發布真正發生的動作。

did 降成原子專屬 predicate：移動／建立須至少一個成功成員，傷害須正量，counter／翻面須指定整體完成，pay 讀 PaymentComplete，evolve 讀 evolved。Declined、Inapplicable、Completed 無結果不是同一狀態。count_of.where 先篩有型別材料快照再計數；objects_of 回資料，follow 才回獲授權新物件。

每輪 repeat 的 receipt 獨立，collect 保序列表。simultaneous 的子 receipt 到整批完成才可讀，不讓後子步驟以先子步驟尚未提交結果決定本批。

付款採可回復交易：合法性預演與提交共用規則管線，取消恢復狀態、RNG、歷史、待機、模式使用及一次性額度。需要玩家輸入的隨機付款不可先公開未提交結果；預演若需要隨機資訊，只在 authority 完成並以同一提交記錄保存。

## 考慮過的選項

| 選項                          | 為何不採／採用代價                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------- |
| 所有成功只存 bool             | Q1776 無法知道成功的是哪個成員；也不能區分拒絕與規則前提不成立，重播和後句都會失真。        |
| 一律 actual>0 代表付款完成    | 會把 CR 允許的零費用誤判失敗，或把只付到部分材料錯判成功；付款需要獨立完整性。              |
| 每張卡自己解讀 did            | 同樣的 counter／move 在不同卡有不同成功口徑，測試只能逐卡修補，不能保證巨集與 inline 一致。 |
| 複製整份 state 到每份 receipt | 容易實作但浪費空間並增加私有資訊外洩面；只保存該指示所需快照與引用即可，完整回復日誌另存。  |

## 後果

成本預演與正式提交需共享核心，不可只有簡單 can_pay 再執行另一套動作。驗收涵蓋零費用、取代支付、材料不足、隨機成本回復、BP03-001 的 X 與 Q1776 的部分成果。

## 未決事項

交易 journal 或 persistent state 的效能選擇待基準量測；typed receipt 的儲存壓縮不得丟失原有單位、材料特徵與付款完整性。
